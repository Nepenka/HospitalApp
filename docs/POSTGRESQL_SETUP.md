# PostgreSQL — подключение, перенос и резервирование, 05.10.2026

## Текущий статус

Добавлен рабочий PostgreSQL-backend приложения: учётные записи, организации, лицензии, ручные финансы, сеансы, устройства, осмотры, отметки удаления, подтверждения синхронизации, архив конфликтов и журналы. ФИО, комментарии, показатели, пароли/хэши и полные клинические снимки остаются зашифрованными AES-256-GCM; технические индексы и метаданные не шифруются. Это гибридная модель: отдельные индексированные строки с зашифрованным payload, не полная нормализация общей карточки пациента.

05.10.2026 на личном компьютере установлен PostgreSQL 18.6 из официального Windows x64 binary-архива EDB. Приложение переключено на PostgreSQL. Перенесены 5 организаций, 7 учётных записей, 6 осмотров и 5 событий журналов. Два осмотра сохранили идентификаторы организаций, которых больше нет в реестре: они не удалены и не перепривязаны к другой больнице. Исходные файлы оставлены без изменений.

Пройдены настоящий SQL-тест двух независимых процессов (конфликт версии, rollback), полный HTTP-прогон сайта в двух независимых Next-процессах с ограниченной ролью БД (комментарии, PDF, tenant/роли, сеансы, финансы, синхронизация/конфликты, одновременное занятие последнего места врача). Все HTTP-данные синтетические, контур отдельный: временная база с суффиксом `_test` удаляется после проверки, рабочая база не используется.

## Ежедневное резервирование

Зарегистрированы задачи Windows текущего пользователя: `AnaFix PostgreSQL` (запуск базы при входе) и `AnaFix Daily Backup` (03:00 и проверка пропущенного запуска при входе). Выполняются скрыто с обычными правами, только пока пользователь вошёл в Windows. Компьютер должен быть включён; это не круглосуточная серверная служба. Планировщик разрешает один экземпляр каждой задачи, повторяет ошибки до трёх раз. Оба фактических фоновых запуска завершились кодом 0; через планировщик проверен и полный цикл, а не только пропуск уже готовой копии. Дополнительно выполнен настоящий холодный запуск: собственный кластер остановлен, вновь поднят задачей Windows, данные и настройки сверены.

Копии: `C:\Users\dlyaw\AnaFixServer\backups\anafix-*.backup.enc`. `pg_dump -Fc` использует согласованный экспортированный снимок, не требует остановки сайта. Архив и ключи приложения находятся внутри внешнего AES-256-GCM-конверта. Отдельная задача восстанавливает последнюю копию в собственную временную БД, сверяет SHA-256 каждой таблицы с тем же снимком и расшифровывает все медицинские/учётные payload. Рабочая БД не перезаписывается; временная БД удаляется. Не сохраняются дампы с открытыми медицинскими данными. Служебный временный дамп с зашифрованными строками находится в защищённом каталоге и удаляется после операции.

`backup-status.json` показывает время создания копии, проверку восстановления и отсутствие внешней копии. Эти данные видны в `/admin/system`; копия старше 36 часов отмечается как устаревшая. Журналы: `scheduled-start.log`, `scheduled-daily.log`; паролей/ФИО в них нет. При ошибке восстановления отчёт не остаётся успешным.

Ручные команды из `web/`:

```text
pnpm db:local start
pnpm db:local check
pnpm db:backup
pnpm db:verify-backup
pnpm db:schedule
pnpm db:local test
pnpm test:postgres:http
pnpm db:local recovery-kit
```

`db:local connect` — повторная проверка/настройка уже установленного локального контура; не очищает непустую БД и не импортирует повторно. Не используется для произвольного production-сервера. Скрипт `setup` ожидает уже распакованные официальные бинарные файлы в указанном каталоге; он не скачивает установщик автоматически.

### Что ещё обязательно для защиты от потери компьютера

Сейчас копии находятся **на том же компьютере**. Вторая независимая копия не настроена: нужно выбрать внешний диск или согласованную сетевую папку. Автоматическая отправка в облако не включалась. Копии пока не удаляются автоматически; срок хранения серверных резервных копий отдельно не согласован (7 дней относятся к локальным offline-копиям браузера).

Подготовлен переносимый зашифрованный `recovery-kit.enc` и отдельный случайный код `recovery-code.txt` в `AnaFixServer`. Комплект расшифрован и применён для тестового восстановления без получения ключей из DPAPI. Для аварийного восстановления нужны резервный архив, этот комплект и код. **Код нужно сохранить отдельно от архивов/комплекта**, например в защищённом менеджере паролей или запечатанной бумажной копии. Не отправлять код в чат, не хранить его на том же внешнем носителе вместе с архивами. После ротации ключей комплект требует обновления. Проверка на другом физическом компьютере ещё не проводилась; полное развёртывание на новом сервере и восстановление выполняются в окно обслуживания, без перезаписи живой БД.

Лимит дампа 128 МиБ снят. Формат v2 (`AFBK0002`) шифрует дамп потоком AES-256-GCM; размеры не приводят к чтению полного дампа в память. Проверен архив 130 МиБ, побайтовое совпадение и отказ при подмене. При восстановлении импорт начинается только после полной проверки authentication tag. Старые v1-копии читаются с ограничением размера legacy-конверта 256 МиБ; новые копии такого ограничения не имеют. Остались ограничения свободного диска/времени, WAL/PITR, HA, внешние уведомления и шифрование диска. RPO — до суток при успешной ежедневной задаче, больше при выключенном ПК/ошибках. Это локальное резервирование, не законченный production-план больницы.

## Настройка без передачи паролей в чат

1. Для другого сервера подготовить PostgreSQL отдельно. Выделить пустую базу, отдельную учётную запись приложения и резервное копирование. Не использовать настройки личного ПК как готовую production-конфигурацию больницы.
2. В `web/.env.local` локально заполнить `DATABASE_URL`, независимые `IDENTITY_DATA_KEY` и `EXAMINATION_DATA_KEY` не короче 32 символов. Для переноса существующих файлов нужны **прежние ключи**. Общие серверные процессы должны использовать одну БД и одинаковые ключи/`AUTH_SESSION_SECRET`; нельзя копировать production-секреты в тестовый контур.
3. Оставить `STORAGE_BACKEND=files` на время подготовки. В `web/` запустить `pnpm db:migrate`. Команда использует только `db/runtime/`, хранит контрольные суммы и выполняет изменения одной транзакцией. Старые `db/*.sql` — архитектурные наброски; **не применять их вместе с runtime-миграциями**.
4. В окно обслуживания остановить записи сайта и сделать резервную копию исходных файлов, журналов и ключей. `pnpm db:import-files` только проверяет исходные зашифрованные данные и показывает количества, не ФИО. `pnpm db:import-files --confirm` импортирует только в пустую runtime-БД; при ошибке откатывает всю транзакцию. Если исходные ключи отличаются от новых ключей БД, задать `FILE_IDENTITY_DATA_KEY` и `FILE_EXAMINATION_DATA_KEY` только в защищённом окружении импортера. Осмотры отсутствующих организаций требуют явного `--preserve-orphans`: сохраняются с прежними tenant-ID, доступ другой больнице не выдаётся. Исходные файлы не удаляются и не изменяются. Журналы тоже переносятся. Локальные IndexedDB-хранилища браузеров этой командой не меняются.
5. Проверить количество организаций, учётных записей и осмотров, вход, права доступа, комментарии, экспорт, повторную синхронизацию, архив и восстановление резервной копии. Только после этого установить `STORAGE_BACKEND=postgres` и перезапустить приложение. Если PostgreSQL недоступен, приложение выдаёт ошибку, а не незаметно создаёт второе файловое хранилище.
6. После новых записей в PostgreSQL нельзя просто переключиться обратно на прежние файлы: они уже отстают. Обратный перенос пока не реализован; восстановление/откат требует отдельного плана.

Для localhost разрешён `DATABASE_SSL_MODE=disable`. Внешний сервер требует `require` с проверкой сертификата; при своей CA заполнить `DATABASE_CA_CERT` PEM-сертификатом. Параметры `sslmode/sslcert/sslkey/sslrootcert` в URL запрещены, чтобы не подменять настройки проверенного TLS. Не отключать проверку сертификата. Не открывать порт БД всему интернету.

Для миграций нужна отдельная привилегированная роль; runtime-роль должна иметь доступ только к нужной схеме/таблицам и sequence, без superuser/DDL. Для локальной установки ограничения уже настроены; для другого сервера их нужно применить отдельно. `pnpm db:migrate` не должен выполняться от runtime-роли — у неё намеренно нет DDL. Программная tenant-проверка реализована; PostgreSQL RLS дополнительно не включён.

## Конкурентная запись и поиск

- Все шаги транзакции выполняются на одном соединении. Общая транзакционная блокировка защищает учётные записи, лицензии, лимиты и отзыв доступа между процессами; клиническая блокировка действует на конкретный осмотр. Проверка версии и запись совмещены; подтверждение offline-операции сохраняется вместе с изменением.
- Повторная передача команды не создаёт дубль. Одна команда не может быть использована с другим содержимым или другим врачом.
- Фильтры по организации, дате и диагнозу, сортировка и обычная пагинация выполняются SQL. COUNT и страница используют один согласованный снимок.
- Поиск подстроки использует tenant-scoped HMAC-токены, индекс кандидатов и точную проверку после расшифровки, с чтением пакетами по 200 строк. Для частых коротких запросов кандидатов может быть много; точный COUNT всё ещё требует проверки их всех. Обычные страницы и списки организаций/сотрудников имеют SQL-пагинацию по 20 строк. Вход/проверка сеанса используют адресные запросы, но identity-мутации пока читают весь учётный набор.
- Общая БД обеспечивает общий лимит входа и транзакционные триггеры аудита/версий; runtime-роль не меняет append-only таблицы. Восстановление проверяет цепочку аудита. Superuser может обойти ограничения; внешние контрольные точки пока не настроены. Для многосерверного выпуска Next нужны одна сборка, согласованный Server Actions key, доверенный прокси/TLS и нагрузочные проверки.

### Новые миграции и обслуживание

`002` — MFA/лимиты/версии/append-only аудит; `003` — явная тестовая отметка; `004` — search index и проекции списков; `005` — транзакционный аудит enrollment и синхронизации. Не изменять уже применённые миграции. После обновления локального контура выполнить `pnpm db:local migrate` в окно обслуживания: перестроение индексов блокирует записи. Эта команда применяет ограничения runtime-прав; простая `db:migrate` на другом сервере не заменяет настройку ролей. Прежние медицинские записи не меняются при переиндексации.

`pnpm test:search` создаёт собственную временную БД с 3002 синтетическими осмотрами и удаляет только её; `pnpm test:backup` проверяет потоковый архив 130 МиБ. Смена ключей и обновление переносимого recovery-kit описаны в [KEY_ROTATION.md](KEY_ROTATION.md); реальные ключи в этом этапе не ротировались.

## Проверки

`pnpm test:database` проверяет шифрование, настройки TLS и модель транзакций без настоящей БД. Это **не** подтверждение работоспособности SQL на сервере.

`pnpm test:postgres` требует отдельно заданный `DATABASE_TEST_URL` к выделенной тестовой БД с именем, оканчивающимся `_test`. Он не использует обычный `DATABASE_URL`, не устанавливает сервер, запускает два независимых процесса, проверяет конфликт версий и rollback. Удаляет только свою синтетическую запись; схему тестовой БД оставляет. На локальном сервере выполняется через `pnpm db:local test`: проверка пройдена. `pnpm test:postgres:http` создаёт собственную пустую временную БД и запускает весь HTTP-smoke в двух Next-процессах; проверка пройдена. Режим `smoke-export.mjs --postgres` требует пустую отдельную тестовую БД, никогда не подключайте его к рабочей.
