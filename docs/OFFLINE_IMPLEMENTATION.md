# Работа без интернета — 04.10.2026

## Согласовано и статус

Offline-режим нужен только на компьютерах больницы. При конфликте обе версии сохраняются до решения врача; автоматического выбора последней правки нет. Согласованы 48 часов доступа и 7 дней хранения синхронизированных копий после последней синхронизации. Черновики, неотправленные данные и нерешённые конфликты автоматически не удаляются; после истечения доступа они блокируются до проверки по сети.

Техническая реализация добавлена; в примере конфигурации `OFFLINE_ACCESS_HOURS=48`, но `OFFLINE_ENABLED=false`. Реальная конфигурация не менялась. Включение требует разрешения больницы, настройки сервера и приёмки управляемых компьютеров; личный компьютер разработчика не считается автоматически разрешённым компьютером больницы.

Раздел открывается по ссылке «Без интернета» на главной странице или по `/offline`. Он использует существующие зелёные цвета, кнопки и календарь сайта, а не дизайн мобильного приложения. Интерфейс доступен на русском и английском.

## Что реализовано

- Подключение только после входа по сети под личной учётной записью врача, обязательной смены первоначального пароля и подтверждения разрешённого компьютера больницы. Администратору организации клинический offline-доступ закрыт. С 03.10.2026 требуется также разрешение/срок в лицензии больницы; есть реестр браузеров и блокировка сетевого подключения без стирания локальных данных. Подробности: [ADMINISTRATION_IMPLEMENTATION.md](ADMINISTRATION_IMPLEMENTATION.md).
- Отдельная парольная фраза от 16 символов. Она не отправляется серверу и не сохраняется приложением. Восстановить несинхронизированные данные при потере фразы нельзя.
- IndexedDB содержит только зашифрованный контейнер, соль и IV. ФИО, осмотры, разрешение доступа, очередь и архив конфликтов находятся внутри шифротекста. Ключ AES-256-GCM получен из фразы через PBKDF2-HMAC-SHA256, 600 000 итераций; при каждой записи используется новый случайный IV. Ключ неэкспортируемый и живёт только в памяти вкладки.
- Законченный осмотр сохраняется локально до отправки. Клинический расчёт, каталог и ввод показателей работают без сети. При передаче сервер повторно проверяет входные данные и пересчитывает заключение: результат клиента не является доверенным.
- Локальная история: поиск без ФИО в URL, диапазон дат, страницы, просмотр критериев, комментария врача и известной даты/времени реакции. Синхронизированный осмотр можно редактировать и мягко удалить; ещё не отправленный осмотр можно исправить без создания дубля.
- Очередь переживает закрытие вкладки и повторную разблокировку. Команда получает постоянный идентификатор; подтверждение и изменение записи сохраняются сервером совместно. Потеря ответа и повторная передача не создают второй осмотр. После начала отправки содержимое команды нельзя изменить до подтверждения.
- Синхронизация вручную и при возвращении соединения, только пока хранилище разблокировано. Записи скачиваются страницами, включая отметки удаления; загрузка не перезаписывает локальные правки. Первая загрузка может быть неполной до завершения синхронизации.
- При конфликте доступны локальная и серверная версии. После явного решения врача обе копии остаются в локальном архиве; выбранная локальная версия отправляется относительно новой версии сервера. Восстановление сервером удалённой записи автоматически запрещено. Полной серверной истории прежних версий этот архив не заменяет.
- Блокировка очищает ключ и данные интерфейса из состояния приложения, включая уход со страницы и окончание разрешённого срока. Данные в IndexedDB не удаляются при истечении доступа. Для восстановления очереди нужен вход по сети тем же действующим пользователем и парольная фраза.
- Очистка локальной копии требует подтверждения, не затрагивает сервер и запрещена при неотправленных записях или нерешённых конфликтах.
- Production service worker кэширует только общую страницу `/offline` без медицинских данных и публичные файлы конкретной сборки. API, персональные страницы, PDF и RSC-ответы не кэшируются. При отсутствии сети переход на страницу сайта направляется к общей offline-оболочке. В разработке этот worker не подключается; старые worker приложения отключаются, чтобы не смешивать сборки.

В разработке отключение legacy worker выполняется через короткоживущий retirement-worker: простого `unregister()` недостаточно для уже открытой вкладки. Он вызывает `skipWaiting`, `clients.claim`, удаляет только публичный Cache Storage `anafix-*` и отключается, не регистрируя обработчик `fetch`. Уже открытые вкладки переходят на сеть; IndexedDB и очередь остаются нетронутыми. Dev-ресурсы используют отдельные адреса `/__anafix_dev_v2/_next/static/`, не совпадающие с прежними URL. Сам механизм проверен модельным тестом; полный браузерный lifecycle пока не принят.

## Ограничения и условия перед внедрением

1. Утверждены 48 часов. Администратор задаёт `OFFLINE_ENABLED=true`, `OFFLINE_ACCESS_HOURS=48` и точный `APP_ORIGIN` без завершающего слеша; в лицензии больницы отдельно разрешает offline и срок до 48 часов. Более длительный срок не включать без нового согласования. До настройки и приёмки реальные данные не подключать.
2. Галочка «компьютер больницы» — подтверждение пользователя, не аппаратная аттестация. До внедрения нужны управляемые больницей устройства/профили браузера, шифрование диска, блокировка ОС, ограничения расширений и локальных пользователей. Реестр браузерных устройств и сетевой отзыв уже есть; аппаратная аттестация и MDM не подключены.
3. Нельзя мгновенно отозвать доступ на отключённом компьютере. Подписанное разрешение ограничено сроком, но часы и данные браузера не являются защищённым источником времени. Проверка отката часов — дополнительная защита, не гарантия против владельца ОС. После возвращения сети offline API проверяет реальное состояние учётной записи, организации и версию пароля. Общий онлайн-реестр сеансов и отзыв после сброса пароля реализованы; привилегированным ролям дополнительно нужна 2FA.
4. IndexedDB не является резервной копией: очистка браузера, приватный режим, нехватка места или потеря компьютера могут уничтожить несинхронизированные записи. Врач должен проверять состояние очереди перед уходом; больнице нужна эксплуатационная инструкция и испытание на своих браузерах. Не закрывать страницу до подтверждения сохранения.
5. В offline-мастере каждый изменённый снимок формы сохраняется зашифрованно, включая текущий шаг и пустые/незавершённые числовые и временные поля. Есть список черновиков, продолжение, явное удаление и защита от перезаписи другой вкладкой. Итоговое сохранение осмотра и удаление черновика выполняются одной локальной записью. Подтверждение врача не восстанавливается автоматически. Дождаться надписи о сохранении перед закрытием: мгновенное завершение процесса ОС может оборвать последнюю запись. Обычная онлайн-форма не начинает незаметно хранить данные локально. Фоновая отправка из заблокированного worker не реализована: ключ ему не передаётся.
6. Синхронизированные копии старше 7 дней очищаются при разблокировке/работе хранилища. Браузер, который закрыт или заблокирован, не имеет ключа и не может выполнить физическую очистку точно в момент окончания срока; она выполняется при следующей разрешённой работе. Копия с черновиком правки защищена от удаления. Неотправленные записи, события экспорта и нерешённые конфликты сохраняются. Решённый локальный архив очищается через 7 дней только после подтверждения передачи решения серверу; обе серверные версии остаются. Срок серверного архива и допустимый объём истории нужно согласовать отдельно. Пять лет для мягко удалённых серверных осмотров не применяются автоматически к браузеру.
7. Добавлен PostgreSQL-backend с транзакционными изменениями, реестром подтверждений и серверным архивом обеих версий конфликта. До настройки настоящей БД работает одно-процессный файловый прототип. Подключение/перенос: [POSTGRESQL_SETUP.md](POSTGRESQL_SETUP.md). Общий security-аудит содержит только метаданные и пока не атомарен с бизнес-записью, не защищён от изменения привилегированным оператором. Резервирование и восстановление требуют отдельной настройки.
8. При смене версии клинического алгоритма старая очередь сохраняется, но отправка блокируется до проверки. Автоматическая миграция клинических результатов не реализована.
9. HTTPS обязателен (localhost подходит для теста). Production secrets должны быть независимыми и управляемыми; смена секрета подписи может сделать старое offline-разрешение непроверяемым, поэтому ротация требует процедуры восстановления очередей. Нужны клиническая приёмка, проверка безопасности и реальный браузерный пилот. Шифрование не защищает разблокированную страницу от XSS, вредоносных расширений или захваченной ОС.

## Экспорт и архив конфликтов

В локальной карточке доступны копирование, печать и PDF на RU/EN. Перед экспортом показано предупреждение о персональных медицинских данных. Несинхронизированная запись обозначается явно; даже синхронизированная копия не гарантирует актуальность серверной версии. PDF содержит локальный шрифт NotoSans; worker готовит публичный шрифт и браузерные chunks заранее. Сам PDF и медицинские ответы в Cache Storage не записываются. PDF, бумажная копия и буфер обмена **не** защищены парольной фразой IndexedDB; их распространение контролирует больница.

До экспорта в зашифрованную очередь записывается идентификатор, вид, время и версия, без текста заключения. После отправки осмотров очередь передаёт метаданные в серверный аудит с проверкой исходного подписанного разрешения, организации и устройства; повторы не создают дубль. Это аудит запроса со слов клиента, а не доказательство фактического завершения печати/скачивания. При ошибке PDF/буфера запись намерения остаётся. Невозможность записать очередь блокирует экспорт.

Сервер сохраняет обе версии при получении конфликта, до выбора врача. Последние 100 конфликтов создавшей их учётной записи можно загрузить отдельной кнопкой; ответ не кэшируется и не выдаётся администраторам или другому врачу. Архив, загруженный этой кнопкой, живёт только в памяти открытого экрана. Локальный выбор передаётся с подтверждением при синхронизации; выбранная локальная версия становится текущей только после успешного применения операции. При новых конкурентных изменениях возможен новый конфликт.

## Проверки

Из `web/`:

```text
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm test:export
pnpm test:offline-policy
```

Unit-тесты используют синтетические записи, fake-indexeddb и модель Web Locks; worker проверяется в модельном окружении. Интеграционные проверки запускают production-сервер с отдельными временными зашифрованными хранилищами, не с реальными `.data`. Проверяются повторная отправка, конфликт/решение/удаление, пересчёт, чужая организация, истечение разрешения, повторная проверка пароля, Origin и запрет подключения без срока. Это не браузерные E2E-тесты.

Браузерная проверка через computer-use в этом окружении не выполнена: запуск средства блокируется ошибкой Windows `apply deny-read ACLs`. Не считать внешний вид, offline-перезапуск браузера, lifecycle обновления worker и очистку памяти при переходах принятыми только по сборке.

## Приёмочный сценарий на тестовых данных

Только в отдельном тестовом окружении задать тестовый срок и точный origin, собрать сайт и запустить `pnpm start`. Войти действующим врачом, открыть `/offline`, дождаться подготовки оболочки, подключить разрешённый компьютер с отдельной фразой, дождаться полной синхронизации. Отключить сеть: создать и сохранить осмотр, проверить историю, заблокировать и перезагрузить страницу; снова открыть её фразой в пределах срока. Вернуть сеть и убедиться, что создана одна серверная запись даже после повторной отправки.

Дополнительно оставить осмотр на шаге показателей с очищенными полями и неполным временем, дождаться статуса сохранения, перезагрузить без сети и продолжить из черновиков. Проверить экспорт RU/EN: предупреждение, кириллицу в PDF, печать, буфер, пометку локальной копии и очередь аудита; после сети — отсутствие дублей. Проверить истечение 48 часов и очистку только синхронизированных копий старше 7 дней, с сохранением черновиков/очереди/конфликтов. Две вкладки одного черновика должны получить конфликт, а не перезаписать друг друга.

На втором тестовом устройстве изменить тот же осмотр по сети; на первом — сохранить другую правку. При синхронизации увидеть обе версии, выбрать одну и проверить локальный архив обеих копий. Отдельно проверить удаление, заполненное хранилище, неверную фразу, истечение срока, другого пользователя, сброс пароля, несколько вкладок, RU/EN, мобильную ширину, клавиатуру и обновление сборки. До согласования и приёмки не использовать реальные медицинские данные.
