# Смена секретов на локальном ПК

Рабочие ключи не менялись автоматически. Ключи и подготовленные планы находятся в защищённом `C:\Users\dlyaw\AnaFixServer`, не в Git/OneDrive. Не отправлять их, `website.env`, recovery-code или DPAPI-содержимое в чат.

Команды выполняются из `web/` с доступным Node.js:

```text
pnpm db:rotation prepare
pnpm db:rotation apply --confirm-maintenance
pnpm db:backup
pnpm db:local recovery-kit --renew
pnpm db:rotation finish
```

1. `prepare` только создаёт DPAPI-защищённый план старой/новой конфигурации, не активирует ключи. Повторная подготовка не перезаписывает незавершённый план. Проверьте независимую копию и доступ к восстановлению прежде чем переходить дальше.
2. Остановите все процессы сайта и договоритесь об окне обслуживания. `apply` отклоняется при открытых соединениях `anafix_app`; это дополнительная проверка, не замена реальной остановки процессов. Никакая новая копия процесса не должна запускаться посреди операции.
3. `apply` создаёт копию и проверяет восстановление, меняет независимые identity/clinical/session секреты, сохраняет прежние ключи и перестраивает поисковые индексы. Изменяются два защищённых файла; они не составляют одну файловую транзакцию. При аварии между ними используйте сохранённый план при остановленном сайте, а не запускайте смешанную конфигурацию.
4. После смены создайте свежую копию и обновите переносимый комплект через `recovery-kit --renew`. Старый зашифрованный комплект сохраняется с уникальным именем; отдельный код восстановления не меняется и не печатается. Перенесите новый комплект вместе с новой независимой копией; код храните отдельно.
5. Архивируйте завершённый план через `finish`, перезапустите все процессы с одной конфигурацией. Старые cookies и offline-разрешения требуют нового сетевого входа. Не удаляйте неотправленные локальные осмотры/черновики ради повторного входа.

До возобновления работы возможен `pnpm db:rotation rollback --confirm-maintenance`. Он запрещён, если в любой медицинской/учётной таблице или архиве версий уже использован новый ключ: возврат к старому набору не должен сделать новые записи нечитаемыми. После новых записей применяйте план восстановления вперёд, а не механический rollback. Старые ключи автоматически не удаляются; при накоплении восьми прежних ключей следующая ротация требует отдельного решения об архивах.

Проверены совместимость новых и legacy envelope, чтение прежних версий с retained keys, отклонение подменённых/неизвестных ключей и независимая подготовка новых ключей. Реальный сценарий apply/rollback с перезапуском всех процессов требует выделенного окна; в этом этапе на рабочей базе не выполнялся. Этот сценарий предназначен для установленного локального контура, не для произвольного удалённого сервера.
