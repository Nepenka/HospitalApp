# АнаФикс Web

Отдельное web-приложение для поддержки врача при оценке острой аллергической реакции. Исходное iOS-приложение находится уровнем выше и используется только как функциональный референс.

## Что уже работает

- обязательный вход перед доступом к медицинской части;
- защищённая HttpOnly-сессия, разграничение ролей и ограничение попыток входа;
- админ-панель на реальных данных: создание организаций, генерация логина/пароля и сброс доступа;
- персональные учётные записи врачей, которыми управляет администратор больницы;
- серверное сохранение осмотров в PostgreSQL с AES-256-GCM-зашифрованными payload; исходные файлы сохранены;
- история пациентов с серверной пагинацией, поиском по ФИО/аллергену, датам и результату;
- печать карточки, копирование заключения и скачивание PDF после предупреждения о персональных данных;
- журнал запросов экспорта без ФИО и содержания осмотра (PostgreSQL либо файловый backend прототипа);
- отдельный комментарий/уточнение врача, не изменяющий рассчитанный диагноз, с сохранением и экспортом;
- необязательные дата и время начала реакции (время Минска), без подмены неизвестного времени полуночью;
- политика хранения мягко удалённых осмотров: 5 лет по умолчанию, настройка отдельной больницы в админпанели; автоматическая окончательная очистка ещё не включена;
- три объяснимых проверки анафилаксии: алгоритм «АнаФикс», NIAID/FAAN и WAO 2020;
- CSP с nonce и базовые HTTP-заголовки защиты;
- пошаговый осмотр: пациент → симптомы → витальные показатели → результат;
- каталог симптомов по шести системам органов;
- возрастные пороги гипотензии, тахикардии и одышки;
- автоматическое влияние SpO₂ и GCS;
- исправленная официальная матрица степеней ОАР 0–5;
- адаптивный интерфейс без усечения клинических формулировок;
- граничные unit-тесты медицинского ядра.
- полный каталог `Symptom.swift` и 12 взаимоисключающих dropdown-групп из `SymptomsViewController`;
- отдельный offline-раздел: зашифрованные локальные осмотры и история, очередь синхронизации, контроль повторных операций и конфликты с сохранением обеих версий; включение запрещено до настройки согласованного срока доступа.

## Локальный запуск

На этом компьютере PostgreSQL 18.6 установлен в `C:\Users\dlyaw\AnaFixServer`, порт `127.0.0.1:55432`. База автоматически запускается при входе в Windows. Секреты находятся вне OneDrive, `web/.env.local` содержит только указатель на локальную конфигурацию. Если база не запущена: `pnpm db:local start`, затем обычный `pnpm dev`. После подключения нужно перезапустить ранее открытый сервер сайта и войти заново; реквизиты учётных записей не менялись.

Копии создаются каждый день в 03:00 (при включённом ПК/входе пользователя), проверяются восстановлением в отдельную базу и находятся в `C:\Users\dlyaw\AnaFixServer\backups`. Независимая внешняя копия ещё не подключена. Команды проверки, комплект восстановления и ограничения: [POSTGRESQL_SETUP.md](../docs/POSTGRESQL_SETUP.md).

```bash
pnpm install
pnpm dev
```

В development-режиме для проверки доступен локальный администратор:

```text
platform-admin
Anafix-Dev-2026!
```

Эта учётная запись не собирается в production. Переменные окружения и требования к секретам перечислены в `.env.example`.

Проверки:

```bash
pnpm test
pnpm typecheck
pnpm lint
pnpm build
pnpm test:export
pnpm test:offline-policy
pnpm test:development
```

Перед `test:development` завершите свой `pnpm dev`: проверка сама запускает отдельный dev-сервер на свободном порту с тестовыми путями хранения и не останавливает пользовательский сервер. Если dev-lock занят, тест завершается без изменений. Production-проверки не заменяют проверку файлов, которые фактически отдаёт режим разработки.

Для разработки JS/CSS используют отдельный префикс `/__anafix_dev_v2`, чтобы не получать прежние файлы из legacy offline-кэша. Если вкладку контролирует старый worker АнаФикс, он заменяется сетевым retirement-worker: тот перехватывает управление, удаляет только Cache Storage с префиксом `anafix-` и отключается. Перезагрузка формы, очистка IndexedDB, медицинских данных и локальной очереди не выполняются. Production-кэширование остаётся привязанным к сборке.

## Архитектура

Административные кабинеты: `/organization` для администратора больницы (обзор, сотрудники, расчёты только своей организации, сеансы/устройства/журнал, настройки) и `/admin` для платформы (организации, лицензии, финансы, безопасность, состояние системы). Административные роли не имеют клинического доступа; врач получает отдельную учётную запись. После обновления нужно повторно войти: старые подписанные cookies без записи в новом зашифрованном реестре сеансов больше не принимаются. Описание, ограничения и приёмка: [../docs/ADMINISTRATION_IMPLEMENTATION.md](../docs/ADMINISTRATION_IMPLEMENTATION.md).

Медицинская логика находится в `src/domain/clinical` и не импортирует React, Next.js или браузерные API. Интерфейс вызывает чистые функции расчёта. Это позволяет независимо тестировать алгоритм и позднее повторно выполнять тот же расчёт на сервере перед сохранением.

Текущая версия — прототип, не готовый для реальных медицинских данных. На этом компьютере установлен PostgreSQL 18.6; импорт, два независимых серверных процесса и локальное резервирование с восстановлением проверены. Добавлены обязательный второй фактор администраторов, общий лимит входа и append-only транзакционный аудит с версиями осмотров. Файловый backend только для однопроцессного демо/тестов, не подменяет БД при сбое. Ручные финансы BYN/USD/RUB и отложенная онлайн-оплата не менялись. Перед реальными пользователями нужны production-развёртывание, независимые копии, клиническая приёмка и внешний аудит: [SECURITY_REVIEW.md](../docs/SECURITY_REVIEW.md).

### Первый вход администратора после обновления

После логина/пароля откроется настройка второго фактора. Добавьте показанный секрет в приложение-аутентификатор, введите его шестизначный код и сохраните резервные коды отдельно. Секрет и резервные коды не отправлять в чат. В дальнейшем нужен пароль и новый код; сброс пароля не отключает второй фактор. Врачу этот административный шаг не требуется. Пока процедура восстановления утраченного фактора не утверждена, особенно важно сохранить резервные коды.

### Дополнительные проверки и обслуживание

`pnpm test:postgres:http` — изолированный PostgreSQL/два процесса; `pnpm test:search` — 3002 синтетических осмотра; `pnpm test:backup` — потоковый архив 130 МиБ; `pnpm test:rotation` — подготовка ключей. `pnpm test:browser` требует уже доступный Playwright (`ANAFIX_TEST_PLAYWRIGHT`) и отдельные тестовые браузеры (`PLAYWRIGHT_BROWSERS_PATH`), не использует личный профиль. Результаты в игнорируемом `.test-artifacts/browser/`. Инструкции смены ключей: [KEY_ROTATION.md](../docs/KEY_ROTATION.md). Подготовленный локальный план не активирует новые ключи.

Offline-раздел `/offline` работает после предварительного подключения разрешённого компьютера больницы по сети. Согласованы 48 часов доступа и 7 дней хранения синхронизированных копий. Черновики, неотправленные данные и нерешённые конфликты автоматически не удаляются. Есть зашифрованное сохранение незавершённой формы, offline PDF/печать/копирование с очередью аудита и серверный архив обеих версий. Реальная конфигурация автоматически не включалась: требуются разрешение организации и приёмка компьютеров. Перезагрузка без сети требует `pnpm build` и `pnpm start`; в `pnpm dev` worker отключён. Инструкции и ограничения: [../docs/OFFLINE_IMPLEMENTATION.md](../docs/OFFLINE_IMPLEMENTATION.md).

Целевая модель данных находится в `db/001_security_foundation.sql`, а подробный план защиты и платежей — в `../docs/SECURITY_ADMIN_ARCHITECTURE.md`.

Актуальный список реализованного, остатка работ и вопросов: [../docs/IMPLEMENTATION_STATUS.md](../docs/IMPLEMENTATION_STATUS.md). Исполняемые PostgreSQL-миграции находятся только в `db/runtime/` (`pnpm db:migrate`). Старые `db/*.sql` — архитектурные наброски, не применяйте их вместе с runtime-схемой.
